# Repository Guidelines

## Git Workflow

- Do not push directly to `main`.
- Put code changes on a feature branch and open a pull request for review.
- Before pushing or opening a PR, inspect `git status`, `git diff`, and recent commits.
- Stage only intentional repo files. Do not include local virtualenvs, caches, generated bytecode, logs, or machine-specific Ableton files.
- Do not force-push, amend shared commits, or rewrite history unless explicitly requested.

## Project Shape

- `MCP_Server/server.py` exposes the MCP tools and validates inputs before sending socket commands.
- `AbletonMCP_Remote_Script/__init__.py` runs inside Ableton Live and implements the socket command handlers.
- When adding a new Ableton operation, update both sides of the protocol in the same change unless it is intentionally server-only.
- Keep command names, parameter names, and result shapes consistent between the MCP server and the Remote Script.

## Ableton API Changes

- Prefer small, explicit wrappers around documented Live Object Model functions and properties.
- Check track/clip bounds and track or clip type before mutating Live state.
- Return JSON-serializable primitives from the Remote Script. Convert Live API objects before sending responses.
- Treat Arrangement View and Session View as separate surfaces; do not assume a clip-slot API works for arrangement clips.

## Verification

- Run `py -m compileall MCP_Server AbletonMCP_Remote_Script` after Python changes.
- Import the MCP server locally with `uvx --from <repo-path> python -c "import MCP_Server.server"` when dependency or packaging behavior changes.
- For Remote Script behavior, prefer a full Ableton restart before testing code changes. Control-surface toggling may leave Python modules cached by folder name.
- A direct socket probe returning a domain error, such as `No clip in slot`, can confirm a command is recognized; `Unknown command` means Ableton is still running an old script.

## PR Readiness

- Do not treat a shallow Ableton smoke test as enough evidence for a public PR when changing unfamiliar Live API behavior.
- Before opening a PR for Ableton API changes, write down the tested Live version, exact manual validation steps, expected results, observed results, and known gaps.
- If the operator is still learning the workflow, do not rely on their confidence alone. Provide reproducible validation steps and keep the branch in the fork until the behavior is understood well enough to review.

## Local Testing Notes

- The installed Ableton Remote Script lives outside this repo. Back it up before replacing it for local testing.
- OpenCode config also lives outside this repo. Do not commit local OpenCode configuration changes here.
- Avoid committing `uv.lock` churn unless dependencies or supported Python versions intentionally changed.
